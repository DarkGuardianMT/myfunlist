# Phase 2C - proposed temporary web-worker diagnostics

**4 November 2026. Review implementation only; no installation, server change or HTTP execution authorized or performed. Open Library remains disabled and activation remains No-Go.** The owner reports Hostinger confirmed that actual CGI/FastCGI worker verification requires HTTP requests. This is owner-supplied hosting guidance, not a new host observation made by this task.

The [readiness plan](BOOK_SEARCH_V2_PHASE2C_HOSTINGER_READINESS.md) deliberately proposed no new public diagnostic endpoint. This package is a **proposed exception**: a temporary, doubly authorized HTTPS endpoint, manually mapped to the actual staging PHP pool. Its URL would be network-reachable on staging; anonymous access must be refused by the server before PHP. The original plan and evidence are preserved. Independent ChatGPT code review and **separate owner approval of exact installation/protection, fixture creation, HTTP execution and removal** are required before any of those operations. Implementation or merge approval alone does not authorize installation or a diagnostic run.

## Isolation and package

The [package](../diagnostics/web-worker/README.md) lives outside `backend/public`, frontend source/static assets and deployment uploads. It adds no route, public file, dependency, workflow or deploy hook. A future deployment may update its tracked source in the private checkout; that does not install or map it. Manual execution must use a separately reviewed copy **outside the checkout/release and every document root/public alias**, avoiding deployment replacement or frontend `rsync --delete`/permission changes. The current deployment and CLI diagnostics remain unchanged.

| File | Purpose |
| --- | --- |
| [endpoint.php](../diagnostics/web-worker/endpoint.php) | Web-only CGI/FastCGI/LiteSpeed adapter; authorizes before reading the body or fixtures. No application/environment loader. |
| [Policy.php](../diagnostics/web-worker/Policy.php) | Protection, expiry, exact POST/body and result policies; bounded request protocol. |
| [Fixture.php](../diagnostics/web-worker/Fixture.php) | Linux/POSIX private-file identity, activity leases, real contention and scoped cleanup. |
| [manage.php](../diagnostics/web-worker/manage.php) | Explicit offline `prepare-reviewed` / `cleanup-after-unmapping` operations; never HTTP management. |
| [config.example.json](../diagnostics/web-worker/config.example.json) | Invalid/disarmed non-executable template; populated `private-config.json` is ignored by Git. |
| [runner.mjs](../diagnostics/web-worker/runner.mjs) | Owner-computer client; verified HTTPS, header-only credentials, fresh connections, no redirects/retries and strict response/count/deadline checks. No request on import or without explicit execution flag. |

No component loads real state, app configuration, sessions, databases or providers. Fixture paths cannot be supplied in requests. No client addresses, PID/inode values, paths, contacts, environment values, secret fingerprints or errors appear in endpoint results. The private fixture proof stores only synthetic nonce, process/file identities and bounded phase state. Real provider caches, counters, secrets and sessions are never test inputs.

## Protection must be established before arming

1. Owner/Hostinger identifies the actual website PHP SAPI/pool, filesystem identity, all public aliases and existing deployment trees. A separate PHP test server/pool does not qualify. Use the same website's real pool with no application `auto_prepend_file`, `auto_append_file`, session auto-start or sessions inherited by the diagnostic. Confirm an external server wall-clock request/body deadline of **at most eight seconds**, body-size limit of 128 bytes and no diagnostic caching. PHP `set_time_limit(5)` is an additional CPU guard; on Unix it does not bound time in system calls. [PHP timeout documentation](https://www.php.net/manual/en/function.set-time-limit.php)
2. Under separate approval, Hostinger establishes an exact temporary server mapping to the private endpoint, protected by **server-level Basic Authentication before PHP for every method/alias/origin path**. Use one short-lived diagnostic-only Basic user and a unique randomly generated password with at least 32 characters. Require HTTPS/TLS verification throughout; deny plaintext access rather than forwarding credentials through a redirect. No secret, credential or authorization value belongs in a URL. Do not rely solely on `.htaccess`, an obscure filename, PHP credential parsing or an unverified control-panel checkbox. Basic requires transport encryption. [Apache authentication guidance](https://httpd.apache.org/docs/2.4/howto/auth.html)
3. The protected server location must supply a fresh 256-bit `MFL_WEB_DIAGNOSTIC_BOUNDARY` **non-client-controlled server parameter**, and verified `AUTH_TYPE=Basic` / `REMOTE_USER`. The expected user is compared by a private SHA-256 value. The marker must not be copied from HTTP headers, query data, a general unprotected location or a client-supplied FastCGI parameter. No fallback to `PHP_AUTH_USER`, forwarded auth/TLS headers or `HTTP_REMOTE_USER` exists. PHP's parsed Basic variables alone are not proof of server authorization. [PHP authentication](https://www.php.net/manual/en/features.http-auth.php), [server/header variable distinction](https://www.php.net/manual/en/reserved.variables.server.php)
4. Require a **different** random 256-bit key in `X-MyFunList-Diagnostic-Key`, checked with `hash_equals` against its private SHA-256 value. It must differ from the boundary marker and Basic password. The caller sends Basic credentials only in `Authorization`; the extra key only in its own header. No cookies, browser Origin, CORS, redirected requests, query strings, path-info, encoded bodies or chunked input are accepted. Request paths must exactly match the configured canonical endpoint path.
5. Verify protection while the package remains **disarmed**. At most three HTTPS POST probes: missing Basic with the independent key, wrong Basic with the key, then valid Basic without the key. The first two must receive the server's 401 Basic challenge and must not enter PHP; prove that privately through Hostinger's request-scoped execution evidence/configuration review, without exporting logs. The third must reach PHP and return the package's fixed 404 denial, with no fixture access. The PHP package never generates a 401/challenge, but the server status alone is still insufficient proof that PHP was not reached. Verify the normal CDN and any origin/alternate mapping are equally protected; if extra probes are needed, stop for a newly approved bounded plan.
6. Confirm no raw headers, bodies, authorization, errors or diagnostic configuration enter logs/traces. Do not export pre-existing host logs containing user/IP data. Server-side denials also need no-store policy. Record only pass/fail evidence for the six `verified` items in the template; absent/false proof prevents arming. These are **operator attestations**, not automatic discovery of server protection. If Hostinger cannot establish the required boundary, actual pool mapping, identity or wall-time limit, do not install/arm; report blocked.

## Future execution budget and success criteria

The owner-computer runner requires Linux private credential storage (parent 0700, JSON 0600, owned, regular, single-link, canonical paths), plus `--execute-owner-approved`. Its ignored `private-client.json` has `owner_approved`, exact HTTPS `url`, `basic_user`, `basic_password` and `request_key`. Keep that file and credentials off Hostinger and out of Git, command arguments, screenshots, trace files and URLs. The private file location is supplied only through `MFL_WEB_DIAGNOSTIC_CLIENT_CONFIG`. Do not use verbose/debug/TLS key logging. No invocation is authorized by this document.

One approved attempt has **six successful diagnostic POSTs**: `attest`, holder A, `ready`, contender B, `visibility`, `cleanup`. The runner sends A asynchronously, confirms readiness on a separate connection, sends B while A still holds its lock, joins both, then runs visibility and cleanup. Connections are fresh, certificate verification stays enabled, requests have five-second total client deadlines, and redirects/retries are disabled. Main phases have a forty-second monotonic budget; joining/drain/one cleanup fit within sixty seconds. Transport uncertainty waits up to the server's eight-second deadline before cleanup and never reports verified cleanup merely from a later successful response.

The endpoint independently permits each action once, at most six non-cleanup admissions and **seven total authenticated protocol admissions**, reserving cleanup capacity after a failed/invalid sequence. Malformed/unauthorized requests are denied before fixture access; external authentication denials are outside that ledger. The operator's total plan is bounded separately: three protection probes, at most seven diagnostic POST attempts and at most two removal checks = **twelve HTTPS POSTs**. No probing, retries, refreshes, load test, polling loop or additional sample is authorized. Need more evidence or insufficient overlap? Stop and seek a new explicit bounded approval.

A uses a three-second monotonic lock-hold deadline, including marker write/sync and acknowledgement, and cannot pass if the deadline is exceeded. Blocking filesystem calls can outlast a PHP loop deadline; the independently verified eight-second server wall-time limit remains mandatory. B must be a distinct actual process viewing the same device/inode, and must get real would-block results during its 150ms bounded contention window. It acknowledges through a different private file. A must observe that acknowledgement **while still holding the lock**. Readiness may arrive before A and wait at most two seconds; readiness alone is never concurrency evidence. Sequential/queued execution, reused PID or absent acknowledgement cannot pass.

Only after joining A/B may C acquire the released lock, read marker A, write/flush/sync/truncate and read marker B. C must be a process distinct from A; scheduling back onto A is inconclusive, not proof of shared visibility. File identity is checked against the original private ownership manifest on every open. All requests hold a shared activity lease; cleanup requires an exclusive lease and exclusive fixture lock, so active workers prevent deletion. Ledger admission locks are nonblocking with a 100ms bound; PHP loop deadlines are monotonic and no request waits indefinitely for a provider/worker slot.

Responses contain exactly one allowlisted `status` and eight booleans: storage access, distinct processes, same inode, confirmed concurrency, contention, release, shared visibility and cleanup. Every PHP response is no-store, JSON and non-reflecting. An attest/ready 200, some true flags, or HTTP 200 alone is **not a cross-worker pass**. The runner only returns `status=pass` after all evidence and complete fixture cleanup are true. It returns inconclusive on any uncertainty. It cannot prove HTTP endpoint/configuration removal; that is a separate owner verification.

## Cleanup, complete removal and failure handling

Cleanup removes only the six exact owned, canonical, single-link synthetic files and empty nonce directory after checking original identities, known marker/control content, bounded ledger and exclusive leases. Unknown files, links, replaced inodes, unsafe modes, incomplete proof or active handles cause refusal with unverified cleanup. No recursive server deletion, repair, state reset or sweeping other directories exists. Named fixtures can survive timeout/host failure; no absolute cleanup guarantee is claimed.

After any failure, stop test requests. If cleanup was safely attempted, do not retry it over HTTP to obtain a green result. First **disable/unmap the diagnostic at server level**, confirm no new requests can enter and wait for the verified eight-second worker bound plus an operator safety margin. Under separate approved cleanup scope, `manage.php cleanup-after-unmapping` can remove only validated owned fixtures after the endpoint expires or its request budget is exhausted; it still refuses active leases, unsafe content or unknown ownership. It does not require rearming or changing expiry. Interrupted/unprovable fixtures require private inspection of only the configured exact nonce workspace; do not remove unrelated files.

Complete removal includes the protected mapping/aliases and diagnostic-only server parameters, the four private PHP files, private config, workspace and client credential file, plus revocation/removal of the diagnostic-only Basic user/password store and independent key. Restore only the diagnostic-specific server changes to the documented pre-install state. Do not rotate application secrets, touch real state, remove ordinary account credentials or alter Open Library settings. Ensure credentials cannot persist in the clipboard, shell history, debug/trace output or exported evidence. Retain only reviewed sanitized booleans, test counts, timestamps and removal status.

Owner/Hostinger privately verifies filesystem/configuration absence and revocation, then makes at most two HTTPS POST checks against the former mapping/any approved alternate route: no diagnostic handler/result or PHP diagnostic execution may remain, including with old credentials. Status alone is insufficient where the application has a generic SPA fallback. If a host/runner is unreachable, cleanup/removal remains **unverified**; escalate to the owner, preserve sanitized failure evidence and keep activation No-Go. No automatic deployment, rollback or reinstallation follows a failure.

## Local validation and limits

Local tests call pure PHP policy/protocol functions using synthetic server arrays and exercise the client through a fake HTTPS transport. They do **not** start an HTTP server, make HTTP diagnostic requests, claim Basic server verification or access Hostinger. Linux-only fixture tests run independent local CLI PHP processes against temporary synthetic storage; they cannot establish real CGI/FastCGI behavior. Windows skips those POSIX tests explicitly rather than weakening production guards.

Run `node --test tests/webWorkerDiagnostics.test.js tests/webWorkerFixture.test.js`, lint every PHP file in `diagnostics/web-worker` plus the two test helpers, and run `node --check diagnostics/web-worker/runner.mjs`. The normal `npm test` includes these tests. Before installation approval, require the complete synthetic suite to pass on an isolated local Linux/PHP environment with POSIX support; Windows skips are not a substitute and no HTTP listener is needed. Security cases cover missing/spoofed Basic/TLS/marker/key signals, absent protection attestations, disarming/expiry, body/path injection, bad output, replay/count/time exhaustion, sequential identity, unsafe cleanup and lost transport. Existing non-destructive provider/API suites remain separate. Exact local results and limitations are recorded in the review handoff.
