# Phase 2C - independent-process CLI locking diagnostics

**Implementation for review; not executed on Hostinger. Open Library remains disabled and activation remains No-Go.** This implements the CLI portion of the [approved readiness plan](BOOK_SEARCH_V2_PHASE2C_HOSTINGER_READINESS.md). It does not provision persistent storage, create an HTTP endpoint or change application/provider behavior. The original preflight workflow, pilot, deployment workflow and historical reports are unchanged.

## Entry point and prerequisites

[staging-cli-lock-diagnostics.yml](../.github/workflows/staging-cli-lock-diagnostics.yml) is a separate manual-only workflow. It requires `main`, explicit `confirm_reviewed=true`, a full `expected_staging_sha`, and an owner-reviewed `storage_parent` alias. Publication and future execution each require separate authorization; neither is part of this review-branch implementation. The existing [preflight workflow](../.github/workflows/staging-open-library-preflight.yml) and its optional subprocess probe remain unchanged.

Available parent aliases are `configured_parent`, `private` and `local_state`, matching the original diagnostic's candidates. No private path is supplied through workflow inputs or printed. The selected directory must already exist, be canonical, non-symlink, owned by the CLI user, readable/writable/traversable and mode 0700, outside the checkout and declared public trees. There is no fallback to another candidate or automatic parent creation. Default `configured_parent` fails when the state path is absent; current verified preflight evidence therefore does not establish a usable target. The owner must separately establish all public aliases, host topology, actual worker access and intended persistent filesystem before authorizing execution.

The workflow uses the existing five staging SSH secrets, including the independently verified host-key pin. [SSH preparation](../scripts/diagnostics/configure-preflight-ssh.mjs) retains strict checking, isolated known-hosts/identity files, no key discovery and no alternate trust sources. The same non-cancelling `deploy-staging` concurrency group prevents overlap with participating deployment/preflight jobs; avoid other deployment/configuration activity during a run. Each remote invocation independently checks the approved deployed SHA. Nothing fetches, resets, installs, deploys or changes permissions on the server's existing files.

Before SSH, the future workflow requires Linux PHP/POSIX/fsync on its **runner** and runs the isolated synthetic fixture/formatter/SSH tests. No staging secrets are available to that test step. These tests must pass before the remote execution step; this does not replace owner review or Hostinger evidence.

## Protocol and protection

The [Node controller](../scripts/diagnostics/run-cli-lock-diagnostics.mjs) launches separate SSH sessions. Every session streams the same [PHP worker](../scripts/diagnostics/cli-lock-worker.php) over stdin; PHP launches no subprocess and uses neither `proc_open` nor `/proc`. It loads only the deployed environment loader, never application bootstrap, providers, sessions or databases. Testing requires the effective CLI pilot flag absent/empty/false; malformed/enabled settings fail. Cleanup may still remove its own safe fixtures after a flag change, but never opens real pilot state for writing.

There are at most eight invocations, with no retries: setup, holder A, readiness observation, contender B, visibility C, reservation D, persistence E and independent cleanup. Setup exclusively creates a uniquely named private run directory and seven mode-0600 files: ownership proof, activity lease, synthetic fixture, file identity, ready/ack controls and reservation witness. A random 128-bit nonce isolates runs. Existing targets are rejected; owner-only permissions, canonical paths, single-link regular files and original device/inode identity are checked. A configured state target inside the run directory, including a resolved alias, is rejected.

A writes/syncs marker A under an exclusive fixture lock, publishes readiness and retains the lock for at most three monotonic seconds. B must observe the same inode in a distinct process, fail nonblocking acquisition with actual would-block evidence for the production-style 150ms window, and acknowledge. A must observe that acknowledgement while still holding its lock. C then acquires, verifies marker A and writes/syncs marker B. D independently verifies B, writes/syncs a synthetic sixty-second reservation plus an exact private witness, and exits without explicit unlock/close. E must acquire and read the unchanged future reservation. Queueing, missing overlap, unknown identity, wrong markers, skipped tests and any incomplete/unsafe response fail closed.

The remote GNU `timeout` process-group watchdog kills an invocation after eight seconds; the runner kills SSH after at most ten seconds. Main phases use a forty-second monotonic budget, reserving drain/cleanup time inside a sixty-second controller attempt. If that window is exhausted, cleanup stays unverified rather than racing possibly active remote work. Every phase checks SHA inside its watchdog. Stderr is discarded after byte counting; stdout has a 1 KiB cap and must exactly match the phase-specific protocol with zero/one exit-code agreement. Only reconstructed allowlisted status lines reach logs/summary. No raw SSH output, fixture content, PID/inode, private path, environment value, secret or fingerprint is exported. SSH receives a minimal local environment without staging secrets.

## Cleanup and interruption

Every ordinary outcome joins outstanding invocations and attempts independent cleanup. All workers retain a shared activity lease; cleanup requires an exclusive lease and fixture lock, verifies ownership, identity and recognized synthetic content, removes only the seven exact files and empty run directory, then verifies observable absence. It never recursively deletes server files or repairs real state. Active workers, unknown content, symlinks/hardlinks, replaced inodes or incomplete setup remain untouched and produce failed/unverified cleanup requiring owner follow-up.

A private runner manifest is written before SSH and updated before each invocation. An `always()` step accepts an already recorded successful cleanup without a ninth invocation. After controller interruption before cleanup starts, it validates the same run/SHA/parent/nonce manifest, rebuilds pinned SSH files from the original secrets, waits twenty seconds for remote watchdog expiry, and attempts cleanup once with a ten-second SSH deadline. This separate recovery window remains bounded even if the original controller is lost. Missing/corrupt manifests, a previously attempted but unverified cleanup, changed configuration/SHA, unreachable hosts or runner loss cannot be reported as cleanup success. A transport timeout/broken connection keeps cleanup **unverified** even if a later bounded removal succeeds. Do not automatically rerun to obtain a green result.

Runner credentials and the manifest are removed in a final `always()` step. Total machine/job loss can prevent that step. The tiny incomplete-setup window can leave an owned but unvalidated fixture directory. For owner follow-up after manifest removal, privately inspect only the selected parent for direct children with that exact run-ID prefix; verify each candidate's nonce/name/owner proof and safe metadata before approving any removal. Do not export the listing, sweep other directories or delete ambiguous/unrelated files. A future approved execution should retain the run ID, parent alias and safe statuses, arrange cleanup ownership in advance and stop on any uncertainty. No absolute cleanup guarantee is claimed across host/runner failure.

## Local validation and limits

Run the focused suite with:

```sh
node --test tests/cliLockDiagnostics.test.js tests/cliLockWorker.test.js tests/preflightReport.test.js tests/preflightSsh.test.js
php -l scripts/diagnostics/cli-lock-worker.php
node --check scripts/diagnostics/run-cli-lock-diagnostics.mjs
```

The controller tests cover every failed phase, timeout/disconnect, stale/malformed/injected output, stderr/overflow, exhausted budget, journal failure, recovery proof and command-input injection. Linux fixture tests use a temporary synthetic checkout/loader and independent local PHP processes only: successful full protocol, unsafe/missing/colliding directories, enabled pilot, wrong inode, symlink/hardlink, unexpected content, real-state collision, partial setup, missing reservation/overlap and cleanup while a holder is active. Unsupported platforms explicitly skip those Linux tests; no production guard is weakened for testing.

On the implementation Windows host, `npm test` passes **302 tests**, with **six Linux/POSIX fixture tests skipped**. The focused suite passes **29 tests**, with those same six skips; PHP/Node syntax, Markdown/internal-link and whitespace checks pass. Existing provider/API suites and the database-safety check pass locally with doubles/fixtures and no database/provider I/O; their negative cases emit expected safe error messages. Actionlint 1.7.12 validates the new workflow with only its unsupported `concurrency.queue` diagnostic suppressed, as in the existing workflow review; shellcheck/pyflakes are unavailable. Linux fixture behavior and remote watchdog behavior are not claimed verified by the Windows run. The manual workflow requires the Linux fixture suite before any future SSH execution.

No Hostinger diagnostic, provider request, web-worker/IP test, local browser preview, deployment or activation was performed. A successful future CLI run still cannot prove web PHP configuration, actual worker locking/access, client-IP behavior, all-instance/egress coordination, restart/deployment durability, policy suitability or activation readiness. Those gates remain in the readiness plan.
