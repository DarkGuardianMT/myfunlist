## Proposed persistent storage

- Owner/Hostinger selects a dedicated application-private persistent directory **outside every document root/alias, checkout/release, dependency directory, frontend upload tree and temporary cleanup area**. Keep the actual canonical absolute location only in private operations configuration. A hidden name or an HTTP deny rule alone is insufficient. Confirm local/shared filesystem type, account isolation, quotas, cleanup exclusions, backup policy and migration retention with Hostinger.
- Prefer the same effective identity for provisioning/maintenance and the actual web workers: directory **0700**, file **0600**, creation umask **0077**; audit ancestor traversal and ACLs. No symlink components, public mappings or unrelated writers. If worker and SSH identities differ, stop for a reviewed least-privilege identity/group/ACL design; do not loosen to world access. The current CLI diagnostic requires owner matching and no group/other access, so a different access design also needs a diagnostic review.
- Only after confirming a genuinely new, inactive installation, create a regular file exclusively, with one link and the modes above, containing `{"version":2,"clients":[],"nextRequestAt":0,"cache":[]}`. Validate bounded schema and actual worker read/write/flush/sync/lock access using a **different disposable fixture** first. No automatic creation, reset or upgrade on application startup/deployment; missing/corrupt/legacy state remains fail-closed.
- Eventually configure `OPEN_LIBRARY_STATE_FILE` privately to the exact canonical file, keeping backend and frontend activation disabled during readiness work. All workers must open the **same inode**, with the same stable secret. Never unlink, rotate, atomically replace or restore that file while any worker may use it: separate inodes permit independent locks and budgets. The application deliberately updates through its locked existing handle.
- The [deployment workflow](../.github/workflows/deploy-staging.yml) resets the checkout, installs Composer dependencies, uploads frontend files with `rsync --delete` and changes frontend permissions. The proposed location avoids those operations, but survival through hosting cleanup, releases, worker recycling and account migration needs separate evidence. At the next independently approved release/recycle, compare identity, permissions, schema and synthetic-fixture continuity privately before/after; publish booleans only. Do not deploy or restart just to complete this plan.
- Keep any backups encrypted/private with short owner-defined retention: state includes pseudonymous client counters and cached public metadata. Snapshot only under a compatible shared lock or while all consumers are quiescent; never restore stale budgets into service. Prefer synthetic fixtures for restore drills. Real-state recovery requires the offline procedure below.

## Locking protocol without proc_open

Implement later as an independently reviewed harness, not a change to pilot semantics. A runner coordinates **independent SSH sessions**, each directly starting one PHP CLI process; PHP never launches a child. Reuse strict verified host pinning, batch mode, exact approved deployed SHA, safe-output allowlisting and deployment exclusion. Stream scripts over stdin; no server script upload. A CLI pass is preliminary evidence only.

1. Reserve a unique private run directory and exclusively created named fixture/control files, separate from real state, sessions and user data. Use the intended storage filesystem, 0700/0600 and synthetic markers only. Record exact artifacts privately; reject existing files, aliases, symlinks, unexpected ownership/link counts or state-target collisions. Unlike the old inherited-descriptor probe, retain the name until every independent opener has closed.
2. Holder A opens `r+b`, obtains `LOCK_EX | LOCK_NB`, writes a marker, truncates, flushes and syncs; then sets a run-specific ready control flag while retaining the lock. Hold for at most three seconds, measured monotonically. Controller starts contender B only after ready; every remote invocation has a ten-second outer timeout, and the entire attempt a sixty-second cap with no automatic retry.
3. B independently opens the same fixture and uses the production-style 150ms acquisition deadline. It must fail acquisition with actual would-block evidence, make no fixture write, and set a separate acknowledgement. A must observe that acknowledgement **while holding the lock**. Confirm distinct process identities and equal device/inode privately, exporting only booleans. Expired readiness, queueing, lock errors, unknown identity or missing overlap is inconclusive/fail, never pass.
4. After A releases, C must acquire, read the exact marker, write a second marker and flush/sync. D independently acquires and verifies that second marker, writes a synthetic future sixty-second reservation, syncs it, then terminates via deliberate `exit` without explicit unlock. E must acquire and observe the unchanged reservation. This verifies process-exit release and durable reservation visibility, not power-loss durability or an actual provider call.
5. Run at most one attempt (maximum eight process invocations, including setup, readiness observation and independent cleanup). Cleanup waits for all handles/processes to finish and verifies exact artifact absence. On timeout/unreachable host, report cleanup unverified and stop. A bounded polling schedule may miss overlap; obtain a separately approved rerun instead of extending hold times or generating load.

For a **web-worker pass**, use at most five collector-bearing requests (A-E) with the same fixture/control protocol in the actual website PHP pool, private worker labels and confirmed overlap. D finishes its request normally without explicit unlock, preserving the ordinary disabled-404 response; this checks request-handle cleanup, not OS process termination. Never kill a serving worker. Separate SSH processes or a different test pool cannot close that gate. Use [PHP's documented advisory-lock behavior](https://www.php.net/manual/en/function.flock.php); every consumer must cooperate, and multithreaded SAPI/filesystem limitations require host confirmation. Never bypass the lock or increase production wait/budget to obtain a green test.

## Risks, cleanup and rollback

- Named fixtures can survive controller/host failure; installing a collector can leak diagnostics if incorrectly scoped. A later implementation must have a private exact-artifact manifest, bounded expiry, independent cleanup connection and fixed allowlisted outcomes. Remove only owned, run-matching regular non-symlink fixtures/control files after all test processes/handles close, then remove the empty run directory; never sweep directories or delete real state. Uncertain identity/content means stop for owner review. Verify collector removal, restored host hook configuration and absence of diagnostic behavior; unreachable host means **cleanup unverified**, even if tests passed.
- Lack of space, permissions, filesystem lock semantics, clock changes, pool saturation or inode replacement can cause safe outages or broken coordination. Fail closed and retain the gate; do not repair active state, evade quotas with extra files/hosts, or expand waits. Host topology/handler/mount/secret changes invalidate earlier evidence and require revalidation.
- During readiness work, abort on the first unsafe condition, stop the harness, close test handles, remove only approved fixtures/collector changes and verify disabled-pilot behavior after privately confirming effective disabled configuration. Do not reverse unrelated host configuration or rotate secrets. No operational rollback is needed for this documentation-only change.
- For a future activated pilot, obtain approval for the prepared rollback: disable backend pilot in every effective worker configuration first, verify propagation and disabled 404, then restore the frontend gate/Google default with an independently approved build/deployment. Allow in-flight requests to drain (transport timeout is eight seconds; confirm host execution bounds), ensuring no worker can still write before touching state. Retain the stable secret/state for investigation; do not reset counters as a rollback shortcut.
- Recovery of damaged/legacy state is a separate **offline** operation: disable every consumer, drain handles, privately back up and validate metadata/content, preserve valid budgets/admissions, and obtain owner review before repair/upgrade/restore. Never hot-replace the inode or restore an old snapshot that grants fresh allowance. If state cannot be preserved safely, remain disabled for a deliberate recovery plan; no automatic empty-state rebuild. Validate through fixtures and actual web access before considering reactivation.
